## The one idea

TCP and UDP are both L4 protocols running on top of unreliable IP. They differ in one structural choice: **TCP maintains connection state**. That state is the lever for all the features (ordering, retransmission, flow control) that make TCP slower but safer. UDP has no state, so it can't fix what IP breaks—but it also doesn't wait for IP to fix it. The cost of TCP is hidden: the three-way handshake, retransmissions on loss, and the coordination overhead when multiple packets fight over the same link. The cost of UDP is visible: you drop messages, or you build your own reliability on top and end up re-inventing TCP.

## The two kinds (and why QUIC matters)

### TCP: reliable, ordered, connected

A TCP connection is a bidirectional agreement: both sides keep state about what has been sent, received, and acknowledged. 

When you call `socket.connect()`, the OS sends a SYN packet and waits for a SYN-ACK. That's two round trips before the first byte of data leaves your machine. But now both sides know:
- The other side is reachable
- Sequence numbers (used to order and deduplicate packets)
- Window size (how much data I can handle without dropping)

If a packet is lost, TCP detects it via timeout (no ACK arrived) or duplicate ACKs (the receiver says "I still expect sequence X") and retransmits. This is reliable, but **every retransmission adds latency**. At scale, that latency is unbounded—one packet loss to an overloaded middlebox can stall all traffic on a connection.

**TCP exists because it works.** E-commerce, banking, file transfer, HTTP/1.1, SSH—anywhere you can't afford to lose messages or have them out of order, TCP is the default.

### UDP: unreliable, unordered, connectionless

UDP is L4 without the overhead. You write a packet, slap a UDP header on it, and send it. No handshake. No state. No retransmission. If the network drops it, you find out only when the other side doesn't reply (and even then, you might not know which packet was lost).

UDP has one advantage: **predictable latency**. You always send one packet and get one response (or none). You never stall waiting for a retransmit timeout. Voice calls, live video, online games, DNS queries—anything where "old data is worthless" uses UDP.

The tradeoff: **you must handle loss yourself**. Video codecs interpolate dropped frames. Voice codecs mute. Game servers re-send state on a timer. DNS clients retry with exponential backoff. You're not eliminating loss; you're making it survivable.

### QUIC: UDP packet format, TCP properties

QUIC (RFC 9000, used by HTTP/3) runs on UDP but reconstructs TCP-like guarantees: connection handshakes, per-stream ordering, retransmission, congestion control. It exists because:

1. **TCP lives in the OS kernel.** Fixing TCP takes OS updates. QUIC is userspace, so CDNs and cloud providers can iterate.
2. **TCP's head-of-line blocking**: if one packet is lost, all data on that connection stalls until retransmit. QUIC has multiplexed streams—a loss on stream A doesn't block stream B.
3. **Handshake cost**: TCP's 3-way handshake (SYN, SYN-ACK, ACK) happens before TLS can even start. QUIC folds the handshake into the first data packet (1-RTT) or even uses a cached server key (0-RTT).

QUIC's cost: operational complexity. More to monitor, tune, and debug. More CPU. Not worth it unless you're Google, Cloudflare, or running millions of connections.

## Picking one

| Scenario | Use | Why |
| --- | --- | --- |
| E-commerce checkout, payments, file transfer | TCP | Message order, delivery, and atomicity matter. Loss is worse than latency. |
| Live video broadcast, voice call, online game | UDP | Old frames are worthless. Jitter is OK. One dropped packet doesn't stall everything. |
| Bulk data transfer (S3, database backup) | TCP | Bandwidth optimization: retransmission is cheaper than re-uploading 1GB. |
| Real-time market data, sensor telemetry | UDP or custom | If you can afford to miss a tick, UDP is simpler. If you can't, consider TCP or QUIC. |
| Internal service-to-service, high throughput | TCP | Operational simplicity. Libraries handle retransmission. Cost is hidden until you hit the limit. |
| Mobile app, unreliable network | QUIC or custom UDP | TCP stalls on every loss. UDP survives, but needs application-level recovery. QUIC balances both. |

## How TCP actually works: the hidden costs

### The three-way handshake

```
Client                                Server
  |------ SYN (seq=x) -------->|
  |<----- SYN-ACK (seq=y, ack=x+1) ---|
  |------ ACK (seq=x+1, ack=y+1) --->|
  |---- (now we can send data) ----->|
```

**Cost: 1 round-trip latency before first byte.** On a 50ms link, that's 50ms wasted. At scale, connection setup is measurable. This is why HTTP keep-alive and connection pooling exist—reuse connections to amortize the handshake cost.

### Sliding window and flow control

TCP doesn't send and wait for an ACK on every packet. Instead:
- Sender: "I'm going to send 65,536 bytes without waiting"
- Receiver: "I can handle 16,384 bytes right now" (window size)
- Sender: "OK, sending 16,384"

This window slides: as the receiver processes data, it sends ACKs that increase the window. The receiver can also shrink the window if it's falling behind (flow control). This prevents a fast sender from overwhelming a slow receiver.

**The cost:** the receiver must keep buffering data, even if the app isn't reading it fast enough. Run out of buffer, window hits zero, sender stops. This is called **backpressure**, and it's necessary but can cascade—if one client backs up, all clients behind it on the same network link back up.

### Congestion control: the invisible throttle

The network between you and the server is shared. TCP assumes: if I don't get an ACK, the network is congested, so I should send slower.

- **Slow start**: send 1 packet, then 2, then 4 (exponential). Double every RTT until loss.
- **Congestion avoidance**: after loss, cut the window in half. Increase slowly.
- **Fast retransmit**: if you get 3 duplicate ACKs, retransmit immediately—don't wait for timeout.

**Why it matters**: if the network is bad (high loss), TCP spends time ramping up, backing off, and re-ramping. This adds latency variance. On a 100ms link with 1% loss, you might see 100ms latency most of the time but 5000ms when a retransmit timeout fires. And you're helping everyone—when you back off, the network link frees up for others.

## The failures that actually page you

### Retransmission timeout (RTO) explosions

Scenario: You have a connection to a database. One packet is lost (cosmic ray, overloaded NIC, whatever). TCP doesn't know if it's lost or just delayed, so it waits for a timeout before retransmitting. Default timeout starts at 1 second and doubles: 1s, 2s, 4s, 8s... By the time the 4th retransmit fires, you've lost 15 seconds of latency. Your application times out at 10 seconds. User sees "connection failed."

Root cause: one packet loss. Impact: cascading application timeouts. This is why:
- Monitoring retransmit rates is critical (they're invisible in application logs)
- Timeout selection matters (too short = false positives, too long = disaster)
- TCP Fast Open and QUIC exist (fewer packets to lose in the handshake)

### Head-of-line blocking

Scenario: You're streaming video over HTTP/2 (which uses TCP). Three packets are in flight:
- Packet A: video frame 1
- Packet B: video frame 2
- Packet C: audio

Packet B is lost. TCP retransmits B before the receiver will even look at C. The audio is stuck waiting for the video frame. On UDP, the audio packet arrives immediately.

This is why HTTP/3 uses QUIC: streams are independent.

### Connection pooling exhaustion

Scenario: Your service opens one TCP connection per request to a backend. After 1,000 requests, you have 1,000 connections. Each uses memory and a file descriptor. The OS has a limit (often 65K file descriptors per process). You hit it. New connections fail with "too many open files."

Worse: each connection that closes goes into TIME_WAIT state (2-4 minutes by default) to catch delayed packets. You can't reuse the port. You run out of source ports (65,536 max per destination IP:port pair). Now you're rate-limited by your own TCP stack.

Root cause: TCP trades CPU (for state management) for memory usage. Connections are expensive. This is why:
- Connection pooling limits exist
- HTTP keep-alive is default
- Kubernetes services round-robin across replicas (spreads connections)

### Congestion collapse

Scenario: The link between your data center and the user is saturated. Every packet you send has a 10% chance of being dropped. You retransmit, adding more traffic. More retransmits. Everyone is sending, no one is getting through. Network throughput drops.

Modern congestion control (BBR, Cubic) is designed to detect this before it happens—but it's still a risk under extreme load. This is why cloud providers rate-limit and use traffic shaping.

## Build it yourself

We'll build two simple demos: a TCP echo server and a UDP echo server, then see how they behave under packet loss and timeouts.

### Step 1: TCP echo server

Save as `tcp_echo.js`:

```javascript
// run: node tcp_echo.js
const net = require('net');

const server = net.createServer((socket) => {
  console.log('Client connected:', socket.remoteAddress);
  
  socket.on('data', (data) => {
    console.log('Received:', data.toString());
    socket.write(`Echo: ${data}`);
  });
  
  socket.on('end', () => {
    console.log('Client disconnected');
  });
  
  socket.on('error', (err) => {
    console.error('Socket error:', err.message);
  });
});

server.listen(3000, 'localhost', () => {
  console.log('TCP server listening on port 3000');
});
```

Run it:
```bash
node tcp_echo.js
```

In another terminal, connect and send data:
```bash
nc localhost 3000
# Type: hello
# Expected output: Echo: hello
```

**What you're seeing**: the client sends, the server receives, sends back, and the client prints it. This is TCP guaranteeing delivery and order.

### Step 2: UDP echo server

Save as `udp_echo.js`:

```javascript
// run: node udp_echo.js
const dgram = require('dgram');

const server = dgram.createSocket('udp4');

server.on('message', (msg, rinfo) => {
  console.log(`Received from ${rinfo.address}:${rinfo.port}: ${msg}`);
  server.send(`Echo: ${msg}`, rinfo.port, rinfo.address, (err) => {
    if (err) console.error('Send error:', err.message);
  });
});

server.on('error', (err) => {
  console.error('Server error:', err.message);
});

server.listen(3001, 'localhost', () => {
  console.log('UDP server listening on port 3001');
});
```

Run it:
```bash
node udp_echo.js
```

In another terminal, send a UDP packet:
```bash
echo "hello" | nc -u localhost 3001
# Expected: no output (UDP doesn't guarantee a reply reaches you)
```

Try again with a listener:
```bash
nc -u -l localhost 3002 &  # Listen for replies
echo "hello" | nc -u -w 1 localhost 3001
```

**What you're seeing**: UDP sent the packet, but if it got lost (or the reply got lost), you'd have no way to know. TCP would retry; UDP shrugs.

### Step 3: Simulate packet loss with TC (traffic control)

On macOS, use `pfctl` (packet filter); on Linux, use `tc` (traffic control). We'll add 50% packet loss to localhost UDP traffic:

**On macOS:**
```bash
# Set up a PF rule to drop packets
echo "dummynet-anchor \"mop\" all
pass out quick on lo0 proto udp from any to any keep state dup-to <mop> in
anchor \"mop\" all {
  dummynet in quick proto udp from any to any pipe 1
  pipe 1 config bw 1000Mbps delay 0 plr 0.5
}
" | sudo pfctl -f -

# Enable PF
sudo pfctl -e
```

**On Linux:**
```bash
sudo tc qdisc add dev lo root netem loss 50%
```

Now run both servers and a client:

```bash
node udp_echo.js &  # UDP server
sleep 1
# Send 10 UDP packets
for i in {1..10}; do
  echo "packet $i" | nc -u -w 1 localhost 3001
  sleep 0.1
done
```

**What you're seeing**: some packets get echoed back, some don't. UDP doesn't retry—you just lose them.

Now compare with TCP:

```bash
node tcp_echo.js &  # TCP server
sleep 1
timeout 5 bash -c "nc localhost 3000 <<< 'hello'"
```

**With TC loss enabled, TCP is slower.** It waits for the retransmit timeout before resending. But the packet eventually arrives. UDP would just drop it.

### Step 4: Timeout and keep-alive (the cost of connection state)

Save as `tcp_with_timeout.js`:

```javascript
// run: node tcp_with_timeout.js
const net = require('net');

const socket = new net.Socket();

socket.setTimeout(2000, () => {
  console.log('Socket timed out after 2 seconds');
  socket.destroy();
});

socket.on('connect', () => {
  console.log('Connected, sending data...');
  socket.write('Hello\n');
});

socket.on('data', (data) => {
  console.log('Received:', data.toString().trim());
  socket.write('Another message\n');
  // If server doesn't respond within 2s, timeout fires
});

socket.on('error', (err) => {
  console.error('Error:', err.message);
});

socket.connect(3000, 'localhost');
```

With the TCP server still running:
```bash
node tcp_with_timeout.js
# Output: Connected, sending data...
# Output: Received: Echo: Hello
# Output: Received: Echo: Another message
# (after 2s of no data)
# Output: Socket timed out after 2 seconds
```

**What you're seeing**: TCP maintains connection state, so we can set a timeout. If the server stops sending, the client knows (because TCP keeps track). UDP would have no idea.

### Step 5: Witness the cost—connection pooling limits

Save as `tcp_connection_leak.js`:

```javascript
// run: node tcp_connection_leak.js
const net = require('net');

let connections = 0;

// Try to open 1000 TCP connections to localhost
for (let i = 0; i < 1000; i++) {
  const socket = new net.Socket();
  
  socket.on('connect', () => {
    connections++;
    console.log(`Connected: ${connections}`);
  });
  
  socket.on('error', (err) => {
    console.error(`Connection ${i} failed:`, err.message);
  });
  
  // Don't close—let them pile up
  socket.connect(3001, 'localhost');
}

setTimeout(() => {
  console.log(`Total connections: ${connections}`);
}, 2000);
```

```bash
node tcp_connection_leak.js
# Output: You'll see several hundred connections before hitting OS limits
# Error: connect ECONNREFUSED (socket pool exhausted)
```

**What you're seeing**: TCP connections consume resources (file descriptors, memory). Open enough of them, and the OS says "no more." UDP would just send packets—no state to leak.

This is the hidden cost of TCP: **every connection you open reserves kernel memory until it closes**. Pooling, keep-alive, and graceful shutdown all exist to manage this.

## Defend your choice

**"Why TCP for databases and file transfer?"**

Because atomicity and order matter. A database write is only safe if every byte arrives in order and without corruption. A file transfer must complete without silent data loss. TCP's handshake and retransmission guarantee both. The latency cost is worth it—it's a one-time setup, amortized over hundreds of queries.

**"Why not just use TCP everywhere?"**

Because TCP stalls on a single lost packet. In live video, a 100ms stall (one retransmit timeout) ruins the call. UDP gets you a video frame 100ms late instead of stalling the whole stream. Video codecs interpolate the gap. Humans tolerate it. TCP would not.

**"When would UDP be the wrong call?"**

When you can't afford to lose data and you can't afford the latency to retry. A financial transaction, a legal contract, a medical record—you need both safety and speed. TCP gives you safety. UDP doesn't. QUIC is the answer, but it's complex to operate.

**"Why not use QUIC everywhere?"**

QUIC adds operational overhead: more CPU, more memory per connection, more to monitor and tune. It's worth it for Google (billions of users, 0.1s latency matters), Cloudflare (tens of thousands of edge servers), or a CDN. For most internal services, TCP's simplicity is worth the latency cost. The boring option (TCP) is correct until you measure and it isn't.

**"What if the handshake timeout is wrong?"**

If you set it too short (e.g., 500ms), you'll see spurious failures—the connection is fine, but you gave up too early. If you set it too long (e.g., 60s), failed connections are slow to detect. Most systems use adaptive timeouts (RFC 6298) that measure round-trip time and scale dynamically. Linux does this by default; your application shouldn't override it unless you have data that proves otherwise.

## Test yourself

1. **Why does TCP need a handshake, and UDP doesn't?** — Because TCP maintains connection state (sequence numbers, window size) that both sides must agree on. UDP has no state, so nothing to negotiate.

2. **You're building a live sports score ticker. A score update is 200 bytes. Which protocol?** — UDP. A 1-second-old score is worthless; a live score 100ms late is fine. Retransmission latency doesn't help. Losing one packet is survivable.

3. **Describe what happens when a TCP packet is lost on a congested link.** — The receiver doesn't ACK it. The sender waits for the RTO (retransmit timeout, ~200-500ms initially) or detects it via duplicate ACKs. Then it retransmits. On a congested link, the retransmit might also be lost, doubling the RTO. This continues exponentially until the packet gets through or the application timeout fires.

4. **Why does HTTP keep-alive exist?** — Because TCP's three-way handshake adds latency (1 RTT before data flows). Keep-alive reuses connections, amortizing this cost over multiple requests. Without it, a 100-request job would spend 100 RTTs just on handshakes.

5. **When would QUIC be worth the complexity?** — When you have millions of concurrent connections (mobile apps, edge nodes), ultra-low RTT requirements (< 50ms), or need to upgrade TLS without OS changes. For most internal services, TCP is simpler and sufficient.
